# Архитектура, границы и DIP

Сценарий → NoteService → INoteStorage ← JSON / SQLite. `src/cli.py` связывает адаптер и сценарии в точке сборки. Сервис не импортирует infrastructure, не знает о файлах, SQL, окружении или терминале.

В теге `pr6-stubs` сохранены пять настоящих заглушек. В теге `pr6-five-scenarios` видны отдельные реализации до рефакторинга C. После рефакторинга функции сценариев остались совместимыми, общие ограничения вынесены в domain/validation.py, правила операций — в domain/service.py. В тестах C `create_autospec(INoteStorage, instance=True)` проверяет вызовы порта и отсутствие записи при ошибке валидации. Неизменяемый Note и копирование снимка защищают загруженное состояние при неудачном edit.

DIP: высокоуровневые операции зависят от абстракции INoteStorage. Низкоуровневые адаптеры реализуют тот же контракт. Конструктор `NoteService(storage)` принимает зависимость извне (constructor injection). Переключение JSON → SQLite меняет только сборку приложения, а не правила сценариев и не их тесты.

## Семантика и надёжность

Заголовок 1–100 и тело 1–10000 символов после strip; поиск использует casefold. UUID4 полный; даты UTC с часовым поясом. None при edit сохраняет поле, явно пустая строка отвергается. Два None означают отсутствие записи и изменения времени. При равных датах list сохраняет исходный порядок (стабильная сортировка). Короткие префиксы UUID не принимаются: нужен полный ID.

JSON: временный файл в том же каталоге, flush/fsync, затем os.replace. Ошибка до замены не портит прежний файл, временный файл удаляется. SQLite: DELETE и INSERT в одной транзакции; сбой INSERT откатывает DELETE. Отдельный тест вызывает реальное нарушение PRIMARY KEY и проверяет восстановление прежних заметок. Соединения закрываются.

Одновременные несогласованные писатели не поддерживаются: load_all/save_all — контракт одного владельца, а не многопользовательская БД. Атомарная замена не является резервным копированием. Переключение бэкенда выбирает другое хранилище; автоматический перенос существующего JSON в SQLite не заявляется и в задании G не требуется.

## Тестирование и CI

Все тесты пяти сценариев параметризованы фикстурой json/sqlite. CLI проверяется через subprocess с отдельным временным хранилищем, в том числе подтверждение/отмена удаления, Enter в edit, повторный ввод, EOF и русские ошибки без traceback. Coverage собирает дочерние процессы через `patch = ["subprocess"]` (pytest-cov 7).

Обёртки имеют 100% покрытия, но бизнес-правила проверяются отдельно: для NoteService генератор требует ≥90%. Порог D — 80% общего покрытия; F — 90% для Must и 70% для остальных; A усиливает порог каждого сценария до 90%. Количество тестов берётся из реального JUnit, параметризованные случаи считаются отдельно.

CI автоматически перезаписывает docs/coverage-report.md и docs/traceability.md из coverage.json и junit.xml на каждом push/PR. Актуальные отчёты загружаются в артефакт scenario-metrics вместе с JSON/XML/HTML покрытия. В Git хранится проверенный снимок отчётов; обновление main после merge повторно проверяет соответствие. Прямые bot-push в защищённую main не используются.
